Blueprint FUUDelivery v2 — pagamentos híbridos sobre PostgreSQL

Revisão crítica do plano original (Svelte · Bootstrap · PHP · Cloudflare · Mercado Pago · BitPay) com a camada de dados reescrita de MySQL para PostgreSQL. O que estava certo permaneceu; o que era frágil foi corrigido e está justificado abaixo.

Stack confirmada por scan do painel · PostgreSQL substitui MySQL/MariaDB em todas as seções

1. O que muda em relação ao plano v1

Dez correções. As cinco primeiras são de integridade financeira — sem elas o restaurante cobra duas vezes ou entrega comida de graça.

Ponto do v1 Problema Correção no v2
Idempotência com SELECT + INSERT e HTTP 409Corrida entre duas abas: os dois SELECT passam antes dos INSERT. E 409 em retry de rede faz o cliente pagar sem saber o resultado.Chave única + INSERT … ON CONFLICT DO NOTHING; a resposta é cacheada e reenviada com 200. Seção 4.

2. Por que PostgreSQL muda o desenho (e não só o DDL)

Trocar o banco só vale se a aplicação usar o que ele tem. Cinco recursos removem código PHP:

  • Índice único parcial — "um pagamento aprovado por pedido" passa a ser uma restrição do banco, não um if em PHP.
  • LISTEN/NOTIFY — tempo real para KDS e painel sem Redis nem servidor de socket.
  • jsonb — resposta crua do Mercado Pago/BitPay guardada inteira e consultável, essencial em disputa.
  • Row-Level Security — isolamento por restaurante no banco: um bug de WHERE deixa de virar vazamento entre lojas.
  • numeric + transações reais em DDL — dinheiro exato e migração atômica (no MySQL o ALTER não faz rollback).
Decisão explícita: ENUM nativo do Postgres só para conjuntos estáveis (payment_method). Status de pedido usa text + CHECK, porque adicionar valor a enum trava DDL em tabela grande e remover valor é impossível.

3. Esquema PostgreSQL (migração 001)

CREATE EXTENSION IF NOT EXISTS pgcrypto;   -- gen_random_uuid + criptografia
CREATE EXTENSION IF NOT EXISTS citext;     -- e-mail case-insensitive

CREATE TYPE payment_method AS ENUM
  ('mp_card','pix_manual','cash','physical_machine','bitpay');
CREATE TYPE settlement_mode AS ENUM ('white_label','split');

CREATE TABLE restaurants (
  id               uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name             text NOT NULL,
  city_ibge_code   char(7) NOT NULL,
  settlement       settlement_mode NOT NULL DEFAULT 'white_label',
  platform_fee_bps int NOT NULL DEFAULT 0 CHECK (platform_fee_bps BETWEEN 0 AND 3000),
  pix_key          text,
  is_open          boolean NOT NULL DEFAULT false,
  created_at       timestamptz NOT NULL DEFAULT now()
);

-- Segredos isolados: nunca em SELECT * de restaurants
CREATE TABLE restaurant_credentials (
  restaurant_id    uuid PRIMARY KEY REFERENCES restaurants(id) ON DELETE CASCADE,
  mp_public_key    text,
  mp_access_token  bytea,          -- pgp_sym_encrypt(token, :key)
  mp_collector_id  text,
  bitpay_token     bytea,
  rotated_at       timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE orders (
  id             bigserial PRIMARY KEY,
  public_code    text NOT NULL UNIQUE DEFAULT upper(substr(encode(gen_random_bytes(4),'hex'),1,8)),
  user_id        uuid NOT NULL REFERENCES users(id),
  restaurant_id  uuid NOT NULL REFERENCES restaurants(id),
  status         text NOT NULL DEFAULT 'cart' CHECK (status IN (
                   'cart','pending_payment','pending_verification','paid',
                   'preparing','ready','delivering','delivered',
                   'rejected','cancelled','refunded')),
  subtotal       numeric(12,2) NOT NULL CHECK (subtotal >= 0),
  delivery_fee   numeric(12,2) NOT NULL DEFAULT 0,
  discount       numeric(12,2) NOT NULL DEFAULT 0,
  total          numeric(12,2) GENERATED ALWAYS AS (subtotal + delivery_fee - discount) STORED,
  payment_method payment_method,
  change_for     numeric(12,2) CHECK (change_for IS NULL OR change_for >= 0),
  machine_type   text CHECK (machine_type IN ('debit','credit')),
  verification_deadline timestamptz,
  created_at     timestamptz NOT NULL DEFAULT now(),
  updated_at     timestamptz NOT NULL DEFAULT now(),
  -- dinheiro exige troco coerente; maquininha exige bandeira
  CONSTRAINT cash_change_valid CHECK (
    payment_method <> 'cash' OR change_for IS NULL OR change_for >= subtotal),
  CONSTRAINT machine_needs_type CHECK (
    payment_method <> 'physical_machine' OR machine_type IS NOT NULL)
);

CREATE INDEX orders_kds_idx ON orders (restaurant_id, created_at DESC)
  WHERE status IN ('paid','preparing','ready');
CREATE INDEX orders_awaiting_idx ON orders (verification_deadline)
  WHERE status = 'pending_verification';

CREATE TABLE payments (
  id              bigserial PRIMARY KEY,
  order_id        bigint NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  provider        text NOT NULL CHECK (provider IN ('mercadopago','bitpay','offline')),
  provider_ref    text,
  amount          numeric(12,2) NOT NULL CHECK (amount > 0),
  platform_fee    numeric(12,2) NOT NULL DEFAULT 0,
  status          text NOT NULL CHECK (status IN
                    ('created','in_process','approved','rejected','refunded','charged_back')),
  status_detail   text,
  raw_response    jsonb,          -- resposta crua: prova em disputa
  created_at      timestamptz NOT NULL DEFAULT now(),
  UNIQUE (provider, provider_ref)
);
-- Regra de ouro: no máximo UM pagamento aprovado por pedido
CREATE UNIQUE INDEX payments_one_approved ON payments (order_id)
  WHERE status = 'approved';

CREATE TABLE payment_proofs (
  id            bigserial PRIMARY KEY,
  order_id      bigint NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  storage_key   text NOT NULL,             -- bucket privado, nunca webroot
  sha256        char(64) NOT NULL,
  phash         bigint,                    -- detecta reuso de print
  bytes         int NOT NULL CHECK (bytes <= 2097152),
  mime          text NOT NULL CHECK (mime IN ('image/jpeg','image/png','image/webp')),
  uploaded_ip   inet NOT NULL,
  review        text NOT NULL DEFAULT 'pending'
                  CHECK (review IN ('pending','approved','rejected')),
  reviewed_by   uuid REFERENCES users(id),
  reviewed_at   timestamptz,
  reject_reason text,
  created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX proofs_reuse_idx ON payment_proofs (sha256);

CREATE TABLE order_events (           -- append-only: auditoria e tracking
  id          bigserial PRIMARY KEY,
  order_id    bigint NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  from_status text,
  to_status   text NOT NULL,
  actor_id    uuid REFERENCES users(id),
  actor_kind  text NOT NULL CHECK (actor_kind IN ('customer','restaurant','system','webhook')),
  meta        jsonb NOT NULL DEFAULT '{}',
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE idempotency_keys (
  key          uuid PRIMARY KEY,
  endpoint     text NOT NULL,
  request_hash char(64) NOT NULL,
  state        text NOT NULL DEFAULT 'in_flight'
                 CHECK (state IN ('in_flight','done')),
  response     jsonb,
  created_at   timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE outbox (                 -- eventos só existem se a transação commitou
  id         bigserial PRIMARY KEY,
  topic      text NOT NULL,
  payload    jsonb NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  sent_at    timestamptz
);
CREATE INDEX outbox_pending ON outbox (id) WHERE sent_at IS NULL;

Figura 1 — Migração 001. users, order_items e fraud_attempts seguem o mesmo padrão (uuid, timestamptz, numeric).

-- Transição de status com trava, auditoria e evento no mesmo commit
CREATE OR REPLACE FUNCTION advance_order(
  p_order bigint, p_to text, p_actor uuid, p_kind text, p_meta jsonb DEFAULT '{}'
) RETURNS text LANGUAGE plpgsql AS $$
DECLARE v_from text;
BEGIN
  SELECT status INTO v_from FROM orders WHERE id = p_order FOR UPDATE;
  IF v_from IS NULL THEN RAISE EXCEPTION 'pedido % inexistente', p_order; END IF;

  IF NOT (v_from, p_to) IN (
      ('cart','pending_payment'),
      ('pending_payment','pending_verification'), ('pending_payment','paid'),
      ('pending_payment','rejected'),  ('pending_payment','cancelled'),
      ('pending_verification','paid'), ('pending_verification','rejected'),
      ('pending_verification','cancelled'),
      ('paid','preparing'), ('preparing','ready'),
      ('ready','delivering'), ('delivering','delivered'),
      ('paid','refunded'), ('delivered','refunded')
  ) THEN
    RAISE EXCEPTION 'transicao ilegal: % -> %', v_from, p_to;
  END IF;

  UPDATE orders SET status = p_to, updated_at = now() WHERE id = p_order;
  INSERT INTO order_events(order_id, from_status, to_status, actor_id, actor_kind, meta)
    VALUES (p_order, v_from, p_to, p_actor, p_kind, p_meta);
  INSERT INTO outbox(topic, payload) VALUES (
    'order.' || p_to,
    jsonb_build_object('order_id', p_order, 'from', v_from, 'to', p_to));
  PERFORM pg_notify('order_changed', p_order::text);
  RETURN v_from;
END $$;

Figura 2 — Única porta de entrada para mudança de status. A cozinha (KDS) lê apenas status IN ('paid','preparing'), o que implementa em uma linha o princípio "cozinha só produz após aprovação".

4. Idempotência correta em datapaymentcard.php

Retry de rede é normal em 4G brasileiro. O contrato passa a ser: mesma chave + mesmo corpo devolve a mesma resposta; mesma chave + corpo diferente é 422; chave em voo é 409 com Retry-After.

$key  = $_SERVER['HTTP_X_IDEMPOTENCY_KEY'] ?? '';
$hash = hash('sha256', $rawBody);
if (!preg_match('/^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/i', $key))
    json_fail(400, 'X-Idempotency-Key deve ser UUID v4');

$row = $pdo->prepare(
  "INSERT INTO idempotency_keys (key, endpoint, request_hash)
   VALUES (:k, 'datapaymentcard', :h)
   ON CONFLICT (key) DO UPDATE SET key = idempotency_keys.key
   RETURNING state, response, request_hash,
             (xmax = 0) AS is_new");        -- xmax = 0 → inserção nova
$row->execute([':k' => $key, ':h' => $hash]);
$id = $row->fetch();

if (!$id['is_new']) {
    if (!hash_equals($id['request_hash'], $hash)) json_fail(422, 'Chave reutilizada com outro corpo');
    if ($id['state'] === 'done') { echo $id['response']; exit; }   // 200 com a resposta original
    header('Retry-After: 2'); json_fail(409, 'Pagamento em processamento');
}
// … cria payments(status='created'), chama a API, grava raw_response,
//    chama advance_order(), e por fim:
$pdo->prepare("UPDATE idempotency_keys SET state='done', response=:r WHERE key=:k")
    ->execute([':r' => $json, ':k' => $key]);

Figura 3 — O truque xmax = 0 distingue inserção de conflito em uma só ida ao banco, sem corrida.

Correção de fato do v1: o card token do Mercado Pago é de uso único e vida curta — a regra "expira 7 dias" do cronograma original não deve ser usada como garantia. Se a chamada falhar por token consumido, o PWA precisa recriar o CardForm, não reenviar o mesmo token.

5. Tempo real sem servidor extra: outbox + LISTEN/NOTIFY

PWA (cliente)            PHP + PostgreSQL                    Painel / KDS
─────────────            ────────────────                    ────────────
upload comprovante  ──►  BEGIN
                         INSERT payment_proofs
                         advance_order(... 'pending_verification')
                           ├─ INSERT order_events   (auditoria)
                           ├─ INSERT outbox         (entrega garantida)
                           └─ pg_notify('order_changed')
                         COMMIT  ──────────────────────────►  sse.php em LISTEN
toast "em análise"  ◄──                                       toastr + som
                                                              SweetAlert de revisão
                    ◄──  advance_order(... 'paid')  ◄──────── [ Aprovar ]
SSE: pagamento OK        pg_cron varre verification_deadline   KDS mostra o pedido
                         com pg_try_advisory_lock

Figura 4 — NOTIFY entrega o aviso instantâneo; a outbox garante que nada se perde se o painel estiver fechado. Rollback apaga os dois juntos.

Na Cloudflare, o endpoint SSE precisa de regra própria: Cache-Control: no-transform, buffering desligado e exclusão do rate limiting — senão o painel do restaurante fica mudo justamente no horário de pico.
